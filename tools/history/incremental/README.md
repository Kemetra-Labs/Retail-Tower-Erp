# tools/history/incremental

Tooling for the **incremental re-import** of the four source products into this repository (RT-710 MR-8; earlier
runs: RT-760, RT-776, RT-831, RT-841). Scratch-only: nothing here pushes, merges into `main`, or writes to GitHub.

Unlike the rest of `tools/history/` (generated by `build.sh`), this directory is maintained by hand.

## Status: re-created, not independently verified

The original RT-831 scripts `reimport-dryrun.sh` v2 and `meta2.sh` were lost (RT-710 c13824). The owner decided on
2026-10-25 to re-create them with new pins (RT-710 owner override). So:

* `reimport-dryrun.sh` and `meta2.sh` here are **new files with new sha256 values**. They are not the originals, and
  the evidence recorded with the originals (for example RT-841 c13602) cannot be reproduced with them.
* They have had only the author's validation (see the PR description). **MR-8 is not ready** until a reviewer who is
  not the author has verified them and a first run on real anchors has passed an independent verification.
* `rt760_check.py` is byte-identical to the RT-760 script (c13129). The verifier is **not** copied here: the trusted
  one is `tools/history/verify_incremental.py` on `main`, checked by sha256.

## Files and pins

`PINS.tsv` lists the sha256 of every file in this directory and the external pins (verifier, `git-filter-repo`),
and records the lost originals for reference only. Check the files:

```bash
cd tools/history/incremental
awk -F'\t' '$1=="file"{print $3"  "$2}' PINS.tsv | sha256sum -c -
```

| File | Role |
| --- | --- |
| `reimport-dryrun.sh` | `anchors`, `run`, `repro`, `selftest`: re-filters each product up to its anchored head, merges it into a clone of Shadow `main`, runs the project-graph and incremental checks, writes a reproducible manifest. |
| `rt760_check.py` | The overlay, crosswalk, tag-gate, LFS, CI-job and incremental invariants used by the script. |
| `meta2.sh` | Builds the single metadata commit (`frozen.tsv`, `crosswalk/*.tsv`) on the dry-run candidate, runs the trusted verifier with its negative controls, twice. Never writes `verify_incremental.py`. |
| `negtest.sh` | Offline fail-closed checks for the dry-run script, on the selftest output. |
| `PINS.tsv` | Pins, as above. |

## What changed from the RT-760 script (`477519cf`)

* **Previous tip.** The previous imported tip is the committed crosswalk row of the frozen sha, proven by the newest
  `(Re-)Import <repo> history (<dir>)` merge reachable from `main` by **any** parent path (the old first-parent walk
  fails once an earlier re-import landed through a GitHub PR merge). Same rule as `base_tip()` in the verifier.
* **No implicit credentials.** The old script exported `$HOME/rt710/askpass.sh` as `GIT_ASKPASS` when present. Now the
  caller sets `GIT_ASKPASS` explicitly if a private read needs it.
* **No machine-specific paths.** `FILTER_REPO` is required; `selftest` takes `SHADOW_LOCAL` and `SELFTEST_SRC`;
  `negtest.sh` takes `NEG_ROOT` and `SHADOW_LOCAL`.

## Prerequisites

WSL Ubuntu on a short native path (for example `~/rt760`), git 2.43.0, Python 3.12.x with PyYAML (6.0.1 vs the
`requirements.txt` pin is the accepted precondition of 2026-10-20), and `git-filter-repo` v2.47.0 fetched from
upstream (`newren/git-filter-repo`, blob `a40bce548d2c`) with the sha256 in `PINS.tsv`. It is not vendored here: the
script refuses any other file. Copy this directory out of the checkout and run the copy; keep its outputs outside any
repository checkout. bash 4.4 or newer is required (Linux/WSL; macOS system bash 3.2 is not supported).

## Use (owner-gated steps in bold)

```text
FILTER_REPO=/path/to/git-filter-repo  PIN_DATE=<run date>T00:00:00Z
1. reimport-dryrun.sh anchors ANCHOR_DIR          # reads live remotes; GIT_ASKPASS set by the caller if needed
2. reimport-dryrun.sh repro   ANCHOR_DIR RUN_ROOT # two runs, identical manifests
3. BASE=... VERIFIER=... MANIFEST_SHA256=... SRC_MIRRORS=... \
   meta2.sh repro RUN_ROOT ANCHOR_DIR META_ROOT   # metadata commit, trusted verifier, two identical builds
4. independent verification by a reviewer who did not write the candidate
5. **push of the re-import branch, PR, merge commit (never squash or rebase)**
```

Steps 1 and 2 read live remotes; step 3 reads only local mirrors. None of them pushes to a remote or changes a source
repository. They write only local scratch copies: the selftest and negtest push into scratch mirrors, and the dry run
fetches Shadow's open branches and PR heads into its own candidate repository for the branch report. New tags are never auto-approved: only the
owner writes `ANCHOR_DIR/approved-tags.tsv`, one line per tag, `prod<TAB>refs/tags/<name><TAB><40-hex source sha>`,
**no comment or blank lines** (the verifier rejects them).

`SRC_MIRRORS` (step 3) is a directory of `<Repo>.git` mirrors with full history and all tags whose `main` equals the
anchored head of each product (for example `git clone --mirror`, taken at anchor time). The dry run's own
`src/<prod>.git` work copies are not usable for this.

## Known limits

* **Shadow `main` is the trust root.** `inventory.py`, `mkcrosswalk.py`, the callbacks, `tools/project-graph` and
  everything else under `tools/` that the dry run executes come from the anchored Shadow `main`, which the overlay
  manifest binds before they run. Only `git-filter-repo` and the verifier are external pins.
* **The imported product subtrees must equal the sources.** The merge step and the verifier require
  `<dir>^{tree}` of the candidate to equal the source tree (and each merge subtree its second-parent subtree). A
  Shadow-only edit inside a product directory (for example added `NOTICE`/`LICENSE` files) makes the re-import fail
  at `merge` until the same change exists in the source repository.
* Never put credentials in `SRC_BASE` or `SHADOW_URL`: `FETCH_HEAD` in the run directories keeps the URL. Use
  `GIT_ASKPASS`.
* Fetched objects are not fsck'd (the git configuration is nulled), and an executable receive hook inside
  `SELFTEST_SRC` would run on the selftest/negtest pushes into scratch copies.
* `newest_import()` mirrors the verifier's `base_tip()` for these inputs; a non-UTF-8 subject on `main` crashes the
  verifier but not the shell function.
* **Fail-late cases** (they stop at `meta2.sh`, never pass): `rt760_check.py` tolerates comment lines and CRLF in
  `approved-tags.tsv` while the verifier does not; a tag added to Shadow between the anchors and the run is caught only
  by the verifier's tag check. Write `approved-tags.tsv` strictly as described above.
* **Tags on commits that are not on the anchored `main`** (tag-only lineage) are refused by the dry run at the
  `tagroot` step: the verifier cannot accept the crosswalk rows they add. Decline such a tag or move it onto `main`.
* **The verifier pin is in `meta2.sh`** (`PIN_VERIFIER_SHA256`, also in `PINS.tsv`). A new verifier needs an
  owner-reviewed edit of both. The selftest ends by running `meta2.sh` on its own output (end-to-end check).
* `write_manifest` in the dry run records an empty value if a helper command inside it fails (for example
  `pgraph.ci-job-missing`), and both runs record the same empty value. Read the manifest, do not only compare it.
* Neither script hashes itself against `PINS.tsv`; run the check command above first. `.gitattributes` here keeps
  the files LF on checkout; on an older CRLF checkout compare `git show <rev>:<path> | sha256sum` instead.
* Validation: author tests, two read-only code reviews and one external review that executed the selftest, negtest
  and its own attacks offline (RT-710). An independent run on real anchors is still required before MR-8.

## Security

* No credential, token, key or local configuration belongs in this directory. Never commit anchors, mirrors, run
  output or `approved-tags.tsv`.
* A secret scan of this directory must stay clean before any change to it is merged.
* The trusted verifier is trusted only through its external sha256 pin (RT-776 F2): hash your own copy against
  `PINS.tsv`; do not run the committed file on trust. On Windows with `core.autocrlf=true` the checked-out file is
  CRLF and hashes differently; hash the committed blob instead:
  `git show <rev>:tools/history/verify_incremental.py | sha256sum`.
